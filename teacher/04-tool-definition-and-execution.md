# 第四课：模型提出动作，程序真正执行工具

更新日期：2026-11-09。后端环境、资产实体与迁移已完成，用户本机确认数据库连接和资产表；当前回到工具主线，资产查询与模型工具调用尚未实现。

## 1. 从生成内容到请求行动

第三课让模型生成结构化分镜。第四课学习让模型请求调用一个本地工具，由程序执行并得到真实结果。

本课不继续扩展逐字段校验，也不调用付费视频服务。第一个工具采用 `search_user_assets`：根据关键词搜索当前用户有权访问的素材，返回实际资产记录。

模型原先不知道素材库里有哪些文件，工具提供真实外部信息。通过资产服务查询 MySQL 中的名称、描述与标签，不声称已经实现视觉识别、语义向量检索或完整素材管理系统。

### 用户资产与项目引用

用户素材库保存上传、导入或生成后收藏的素材；项目引用资产，分镜再引用所选素材 ID，不必复制同一文件。上传、列表、预览和删除是产品基础功能，草案自动保存也由程序负责，不为演示 Agent 强行改成模型决策。

工具输入先采用 `query` 关键词，可按需要增加素材类型；用户身份由可信运行环境提供，不由模型指定。演示阶段暂不实现登录与接口鉴权，由服务端提供固定演示用户上下文；产品仍保留用户归属关系，不宣称已实现认证隔离。

结果包括资产 ID、名称、类型、描述和必要的资源引用；使用资产 ID 与必要的 COS 资源引用。只返回实际匹配记录，无结果时返回空列表；多个候选需要用户选择时，不把模型猜测当作已确认选择。

素材文件存 COS，记录存 MySQL；端到端验收时确认对象实际存在且可访问。NestJS、TypeORM 和 MySQL 最小链路已验证。先学习数据库记录搜索，COS 接入和真实文件预览后续补齐；仅有记录的测试素材须明确标为测试数据，不能声称已验证文件可用。完整上传界面和 Embedding 留到后续课程。

## 2. 一个工具有三部分

| 部分 | 谁使用 | 内容 |
|------|--------|------|
| 工具声明 | 模型 | 名称、用途、参数的 JSON Schema |
| 工具调用请求 | 执行系统 | 调用 ID、工具名称、模型给出的参数 |
| 工具实现 | 程序 | 根据参数执行本地函数，返回真实结果 |

模型看到的是工具声明，并不因此获得函数执行权。声明工具也不等于程序已注册同名实现；两者需要对应。

模型可以根据工具名称、说明、参数和当前上下文提出调用。我们只能观察实际请求与结果，不把模型对决策的解释当作其内部推理过程的完整证明。

## 3. 用短剧工坊串起来

场景：用户要求“用我素材库里的红衣女主参考图，规划一个雨夜重逢的故事”。

1. 程序准备用户需求，以及 `search_user_assets` 的工具声明；不提前把整个素材库塞进上下文。
2. 请求模型，模型可能返回正式工具调用。
3. 执行系统根据工具名称查找已注册的函数。
4. 对调用参数做必要检查，然后在当前用户可访问的素材中执行搜索。
5. 终端展示调用 ID、工具名称和真实搜索结果。

本课先做到“拿到请求并执行”。第五课再保存模型的调用消息、追加对应工具结果、再次请求模型，组成反馈循环。

直接在代码里调用搜索函数，也是合法程序行为，但它不是“模型选择工具”的演示；两个阶段要分别验证。

## 4. JSON 输出和工具调用的区别

第三课的 JSON 是回答内容，放在 `message.content` 中，供业务解析。

第四课使用接口专门的工具调用机制。不能因为普通回答里出现工具名称或一段 JSON，就自行认定模型发起了正式工具调用。

| 形式 | 意义 |
|------|------|
| 普通文本“我去搜索一下” | 一段回答，不执行工具 |
| 内容 JSON 中写着工具名 | 仍是普通回答数据，除非业务明确设计了另一种协议 |
| API 正式工具调用字段 | 识别为调用请求，再进入查找、检查和执行 |

因此需要扩展当前 Gateway：它不能再把所有响应都当作非空文本。工具调用响应可能没有回答文本，却有有效调用请求；业务结果类型必须能表达两者，具体协议在编写时核对官方文档。

本课不把第三课的 JSON 输出模式默认套在所有工具任务上。输出格式约束和工具选择是不同配置。

## 5. 注册与执行分别是什么？

注册表维护“允许调用的工具名 → 声明与执行函数”的对应关系。

执行器接到请求后，按名称查找、解析参数、进行必要检查、执行函数并记录结果。未知工具不执行；参数无法解析时清晰报错。不根据模型返回的任意名字导入模块，也不执行任意代码。

参数检查限于本工具真正使用的输入，不在本课扩展一套复杂防御框架。前一课的分镜质量、创作约束仍以提示词和输出协议为主。

## 6. 学习与编写顺序

1. 先按[项目目标与架构约定](./project-goals-and-scope.md)搭建最小 NestJS 与 TypeORM/MySQL 连接，建立资产记录和 COS 真实样本；再通过资产服务验证关键词匹配与无结果，不调用模型。
2. 为函数补工具名称、用途说明和参数 Schema，理解 Schema 是说明而不是执行代码。
3. 建立最小注册表与执行入口。
4. 扩展 Gateway 的工具声明输入和工具调用输出，区分回答与调用请求。
5. 用户运行一次真实模型请求，观察模型提出的工具名和参数，再由程序执行。
6. 验证普通回答不误执行、未知工具不执行、坏参数不直接进入函数。核心正常链路通过后，不无目的堆测试。

演示工具选择时，可以在 API 支持范围内显式要求调用，用于验证链路，但要标明这是受约束的调用实验；不能把它说成模型完全自主选择。随后再观察自动模式。

## 7. 本课理解起点

先区分：工具声明是给模型看的“说明书”，工具实现是由程序执行的“函数”。二者通过工具名建立对应关系。

工具调用请求表示模型提出动作；终端出现真实工具执行结果，才说明程序执行了动作。本课完成后仍不等于已实现完整 Agent Loop。

## 当前小步：资产查询服务

先在 `src/assets/assets.service.ts` 实现普通业务查询，由 `@InjectRepository(Asset)` 注入 Repository；在 AssetsModule 注册并导出服务，后续 HTTP 接口和工具复用它。

第一步按 ownerId 限定范围，按一个关键词匹配名称或描述，按更新时间倒序最多返回 10 条；空关键词返回空列表。先不加标签搜索、向量检索或图片内容识别。查询条件使用参数绑定，匹配名称与描述的 OR 条件放在括号内，确保两者都受 ownerId 条件限制。

ownerId 来自服务端上下文，不是模型可任意指定的工具参数。当前只是业务服务方法，尚未注册工具，也未发生模型调用。服务完成后，通过少量明确标注的样本记录验证命中、无结果及用户范围，再接工具协议。

## 通用工具契约与组装（2026-11-10）

已确定搜索与生成两类工具，因此注册表不得绑定搜索工具或识别 query 等业务参数。统一 AgentTool 契约包含 definition 与 execute(input, context)。模型输入作为 unknown 进入各工具的执行边界，由工具检查自身参数；可信用户上下文独立传递。

ToolsModule 注入各具体工具，并通过 AGENT_TOOLS 标识提供工具实例列表。ToolRegistry 只依赖该列表，建立按名称索引的 Map，检查重复名称、提供声明、拒绝未知名称并分发执行。新增生成工具时变更模块组装列表，不改注册表分发逻辑。

教学按契约、具体工具适配、注册表、模块组装顺序推进，但每一步均以完整职责划分为依据。当前契约不是完整 Harness：调用 ID、工具结果消息、审批、预算和重试在相应运行层课程实现；未来生成工具接入真实付费操作前必须接上确认与预算控制。

## 正常链路验证（2026-11-10）

用户提供 `POST /api/agent/run-once` 的真实返回：输入“请从我的素材库搜索墨墨，列出候选素材”，模型返回正式 `search_user_assets` 调用，arguments 为 `{"query":"墨墨"}`。程序返回六条墨墨姿态资产（抱歉、庆祝、思考、讲解、招手、探头）。toolResults 中的 toolCallId 与模型调用 id 一致。

这验证了模型请求、Gateway 协议转换、注册表分发、搜索工具与资产服务数据库查询的正常链路。text 为空符合本轮只有工具调用的响应形式；结果尚未回传模型，没有生成最终自然语言答复，也没有验证素材图片可访问性。

正常链路达到第四课核心目标；无结果、未知工具、无效参数和重复名称等分支尚未完成运行验证，不能标为全部通过。第五课再实现工具结果消息回传和后续模型请求。
