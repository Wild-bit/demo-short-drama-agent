### 一、这节课最终做成了什么

建立 NestJS HTTP 服务，连接 Docker MySQL，创建资产记录及查询服务，并把查询封装成模型可请求的工具。模型提出正式调用后，程序按名称找到实现、检查参数、执行数据库查询并返回真实结果。

第四课的终点是“模型提出动作，程序执行”。工具结果回传模型并继续循环属于第五课。当前源码已经包含后续课程改动，因此重新运行现有接口会得到第五课的最终回答，不会重现第四课当时只执行一轮的返回。

### 四、一条完整的第四课调用路径

```text
用户：搜索墨墨
→ Controller 接收需求，服务端提供 userId
→ AgentService 向模型提供需求与工具声明
→ 模型返回 search_user_assets 和 query 参数
→ Gateway 转成内部 ToolCall
→ 注册表查找工具
→ 搜索工具检查参数
→ AssetsService 按 userId 与关键词查询 MySQL
→ 返回真实候选元数据
```

模型不知道数据库中有哪些记录，也看不到工具函数源码。名称、描述、参数 Schema 和系统规则帮助它判断何时调用；程序真正负责执行。

### 五、最容易混淆的概念

- 工具声明是说明书，工具实现是代码，正式工具调用是模型发出的结构化请求。普通文本“我去搜索”不会自动执行。
- JSON 回答属于 content，正式工具请求属于工具调用字段，不能混为一谈。
- 参数 Schema 帮助模型生成参数，运行时仍需检查输入。当前搜索工具只接受一个非空 query，不允许任意额外字段。
- 工具注册表处理通用分发，不理解 query 等业务参数；具体工具负责自己的参数检查。
- Map 的键唯一不代表重复注册会报错，直接 set 会覆盖旧值，所以必须显式检查。
- userId 来自可信执行上下文，不让模型自由指定。当前固定演示用户不等于已经实现登录鉴权。
- 当前查询按名称、描述匹配，返回标签但不按标签检索，不是 Embedding 或视觉识别。
- 资产元数据在 MySQL，文件计划放 COS；查到记录不代表真实文件可读。

### 七、基础设施配置与排障

#### NestJS 编译与运行

项目保留 ESM 和 `@/` 路径别名。Nest 依赖装饰器及构造函数元数据，使用 TypeScript 编译后运行。`pnpm dev` 监听源码，编译成功后通过 `dev:start` 改写导入路径并重启服务。`pnpm build` 负责清理、编译和改写路径。`pnpm start` 直接运行已构建的 JavaScript。

可选的宿主机运行方式：先准备依赖和 MySQL，再执行 `pnpm typecheck`、`pnpm dev`。宿主机默认 API 端口为 3000，可由 PORT 覆盖；不要误认为容器对外也是该端口。`pnpm build` 生成构建产物，`pnpm start` 运行产物。原终端模型演示已移除。

TypeScript 7 曾导致 tsc-watch 使用包子路径查找编译器时报 ERR_PACKAGE_PATH_NOT_EXPORTED。当前 dev 脚本用 `--compiler "$PWD/node_modules/typescript/bin/tsc"` 指定文件入口，适用于当前 macOS shell 环境。

#### MySQL 配置与数据卷

compose.yaml 使用 MySQL 8.4、独立业务账号、健康检查与命名数据卷。配置由 database.config.ts 读取，DatabaseModule 注册连接池。

| 变量 | 宿主机默认值或用途 |
|---|---|
| MYSQL_HOST | 127.0.0.1；API 容器内由 Compose 覆盖为 mysql |
| MYSQL_PORT | 3307；API 容器内覆盖为 3306 |
| MYSQL_DATABASE | short_drama |
| MYSQL_USER | short_drama，应用业务账号 |
| MYSQL_PASSWORD | 应用账号密码 |
| MYSQL_ROOT_PASSWORD | 仅初始化使用，不作为 API 连接凭证 |

MySQL 镜像仅在首次初始化数据目录时创建账号与数据库；已有卷时修改 .env 不会自动改掉数据库中的密码或库名，需通过数据库操作同步。不要通过删除卷解决普通配置问题。

数据库健康检查用业务账号执行 SELECT 1；启动连接失败会导致应用无法启动，启动后数据库检查失败返回 HTTP 503。

#### 容器挂载与环境变量

Compose 使用 Dockerfile 的 development 阶段，源码 src 可写挂载，package.json 与 TypeScript 配置只读挂载，dist 和 Linux 依赖保存在容器内，不复用宿主机 node_modules。源码修改由开发命令监听、编译并重启；依赖或 Dockerfile 改动后重新执行 `pnpm docker:up` 构建镜像。配置有热更新机制不等于已经实测所有修改均生效。

Compose 从宿主机 .env 读取配置，只向 API 注入所需业务数据库与 DeepSeek 变量，不注入 root 密码。.env 被 .dockerignore 排除。环境变量修改后需重新创建容器配置。

Dockerfile 另有 runtime 阶段，但当前 Compose 使用开发阶段，不代表已完成生产部署。早期依赖安装曾使用 --no-frozen-lockfile；安装可复现性应以当前 Dockerfile 和锁文件为准，不能只凭历史搭建成功作保证。

#### 迁移与常见故障

迁移脚本内包含编译及导入路径改写，生成的时间戳-SchemaChange.ts 通过源码挂载直接写入宿主机。生成只对比结构，不执行迁移；先审查 up/down，再执行 db:migrate。无结构差异时无需生成新文件。

若调整 Compose 挂载配置，在数据库已经启动的前提下，可用以下命令重建 API 容器配置：

```bash
docker compose up -d --no-deps --force-recreate api
```

- Docker socket 不存在或无法连接引擎：确认 Docker Desktop 已启动并就绪。
- 助手环境曾遇到网络、FSEvents 和端口权限限制；这些限制不能证明用户本机环境失败。以实际执行输出为准。
- `docker compose config --quiet` 只验证配置，不验证镜像构建、数据库连接或 HTTP。避免输出展开的完整配置以免泄露密码。

## 1. 从生成内容到请求行动

第三课让模型生成结构化分镜。第四课学习让模型请求调用一个本地工具，由程序执行并得到真实结果。

本课不继续扩展逐字段校验，也不调用付费视频服务。第一个工具采用 `search_user_assets`：根据关键词搜索当前用户有权访问的素材，返回实际资产记录。

模型原先不知道素材库里有哪些文件，工具提供真实外部信息。通过资产服务查询 MySQL 中的名称、描述与标签，不声称已经实现视觉识别、语义向量检索或完整素材管理系统。

### 用户资产与项目引用

用户素材库保存上传、导入或生成后收藏的素材；项目引用资产，分镜再引用所选素材 ID，不必复制同一文件。上传、列表、预览和删除是产品基础功能，草案自动保存也由程序负责，不为演示 Agent 强行改成模型决策。

工具输入先采用 `query` 关键词，可按需要增加素材类型；用户身份由可信运行环境提供，不由模型指定。演示阶段暂不实现登录与接口鉴权，由服务端提供固定演示用户上下文；产品仍保留用户归属关系，不宣称已实现认证隔离。

结果包括资产 ID、名称、类型、描述和必要的资源引用；使用资产 ID 与必要的 COS 资源引用。只返回实际匹配记录，无结果时返回空列表；多个候选需要用户选择时，不把模型猜测当作已确认选择。

素材文件存 COS，记录存 MySQL；端到端验收时确认对象实际存在且可访问。NestJS、TypeORM 和 MySQL 最小链路已验证。先学习数据库记录搜索，COS 接入和真实文件预览后续补齐；仅有记录的测试素材须明确标为测试数据，不能声称已验证文件可用。完整上传界面和 Embedding 留到后续课程。

## 2. 一个工具有三部分

| 部分 | 谁使用 | 内容 |
|------|--------|------|
| 工具声明 | 模型 | 名称、用途、参数的 JSON Schema |
| 工具调用请求 | 执行系统 | 调用 ID、工具名称、模型给出的参数 |
| 工具实现 | 程序 | 根据参数执行本地函数，返回真实结果 |

模型看到的是工具声明，并不因此获得函数执行权。声明工具也不等于程序已注册同名实现；两者需要对应。

模型可以根据工具名称、说明、参数和当前上下文提出调用。我们只能观察实际请求与结果，不把模型对决策的解释当作其内部推理过程的完整证明。

## 3. 用短剧工坊串起来

场景：用户要求“用我素材库里的红衣女主参考图，规划一个雨夜重逢的故事”。

1. 程序准备用户需求，以及 `search_user_assets` 的工具声明；不提前把整个素材库塞进上下文。
2. 请求模型，模型可能返回正式工具调用。
3. 执行系统根据工具名称查找已注册的函数。
4. 对调用参数做必要检查，然后在当前用户可访问的素材中执行搜索。
5. 终端展示调用 ID、工具名称和真实搜索结果。

本课先做到“拿到请求并执行”。第五课再保存模型的调用消息、追加对应工具结果、再次请求模型，组成反馈循环。

直接在代码里调用搜索函数，也是合法程序行为，但它不是“模型选择工具”的演示；两个阶段要分别验证。

## 4. JSON 输出和工具调用的区别

第三课的 JSON 是回答内容，放在 `message.content` 中，供业务解析。

第四课使用接口专门的工具调用机制。不能因为普通回答里出现工具名称或一段 JSON，就自行认定模型发起了正式工具调用。

| 形式 | 意义 |
|------|------|
| 普通文本“我去搜索一下” | 一段回答，不执行工具 |
| 内容 JSON 中写着工具名 | 仍是普通回答数据，除非业务明确设计了另一种协议 |
| API 正式工具调用字段 | 识别为调用请求，再进入查找、检查和执行 |

因此需要扩展当前 Gateway：它不能再把所有响应都当作非空文本。工具调用响应可能没有回答文本，却有有效调用请求；业务结果类型必须能表达两者，具体协议在编写时核对官方文档。

本课不把第三课的 JSON 输出模式默认套在所有工具任务上。输出格式约束和工具选择是不同配置。

## 5. 注册与执行分别是什么？

注册表维护“允许调用的工具名 → 声明与执行函数”的对应关系。

执行器接到请求后，按名称查找、解析参数、进行必要检查、执行函数并记录结果。未知工具不执行；参数无法解析时清晰报错。不根据模型返回的任意名字导入模块，也不执行任意代码。

参数检查限于本工具真正使用的输入，不在本课扩展一套复杂防御框架。前一课的分镜质量、创作约束仍以提示词和输出协议为主。

## 6. 学习与编写顺序

1. 先按[项目目标与架构约定](./project-goals-and-scope.md)搭建最小 NestJS 与 TypeORM/MySQL 连接，建立资产记录和 COS 真实样本；再通过资产服务验证关键词匹配与无结果，不调用模型。
2. 为函数补工具名称、用途说明和参数 Schema，理解 Schema 是说明而不是执行代码。
3. 建立最小注册表与执行入口。
4. 扩展 Gateway 的工具声明输入和工具调用输出，区分回答与调用请求。
5. 用户运行一次真实模型请求，观察模型提出的工具名和参数，再由程序执行。
6. 验证普通回答不误执行、未知工具不执行、坏参数不直接进入函数。核心正常链路通过后，不无目的堆测试。

演示工具选择时，可以在 API 支持范围内显式要求调用，用于验证链路，但要标明这是受约束的调用实验；不能把它说成模型完全自主选择。随后再观察自动模式。

## 7. 本课理解起点

先区分：工具声明是给模型看的“说明书”，工具实现是由程序执行的“函数”。二者通过工具名建立对应关系。

工具调用请求表示模型提出动作；终端出现真实工具执行结果，才说明程序执行了动作。本课完成后仍不等于已实现完整 Agent Loop。

## 已实现：资产查询服务

先在 `src/assets/assets.service.ts` 实现普通业务查询，由 `@InjectRepository(Asset)` 注入 Repository；在 AssetsModule 注册并导出服务，后续 HTTP 接口和工具复用它。

第一步按 userId 限定范围，按一个关键词匹配名称或描述，按更新时间倒序最多返回 10 条；空关键词返回空列表。先不加标签搜索、向量检索或图片内容识别。查询条件使用参数绑定，匹配名称与描述的 OR 条件放在括号内，确保两者都受 userId 条件限制。

userId 来自服务端上下文，不是模型可任意指定的工具参数。当前只是业务服务方法，尚未注册工具，也未发生模型调用。服务完成后，通过少量明确标注的样本记录验证命中、无结果及用户范围，再接工具协议。

## 通用工具契约与组装（2026-11-10）

已确定搜索与生成两类工具，因此注册表不得绑定搜索工具或识别 query 等业务参数。统一 AgentTool 契约包含 definition 与 execute(input, context)。模型输入作为 unknown 进入各工具的执行边界，由工具检查自身参数；可信用户上下文独立传递。

ToolsModule 注入各具体工具，并通过 AGENT_TOOLS 标识提供工具实例列表。ToolRegistry 只依赖该列表，建立按名称索引的 Map，检查重复名称、提供声明、拒绝未知名称并分发执行。新增生成工具时变更模块组装列表，不改注册表分发逻辑。

## 已完成小步：拒绝重复工具名（2026-11-12）

### 要解决的问题

目前 `ToolRegistryService` 的构造函数遍历工具列表，直接调用 `Map.set(name, tool)`。Map 的键唯一，但重复设置同一个键会替换原值，并不会自动报错。

例如素材搜索工具与另一个误配置的工具都叫 `search_user_assets`，后注册的工具会覆盖前一个。此时程序能启动，模型看到和实际执行的却可能是错误工具。工具名既用于向模型声明能力，也用于程序查找实现，需要在组装阶段发现冲突。

### 本步输入、输出和执行过程

- 输入：`ToolsModule` 注入的 `AgentTool[]`，其中包含各工具的声明与执行方法。
- 正常结果：所有名称唯一，注册完成；现有搜索工具的行为保持不变。
- 冲突结果：发现第二个同名工具时，抛出包含该名称的错误，停止注册；在当前 NestJS 注入流程中，这会使应用启动失败。

执行顺序：读取工具名 → 检查 Map 中是否已有该名称 → 已有则报错 → 没有则注册。

这与执行时的“未知工具”检查分工不同：重复名称是开发者组装工具时的错误；未知工具是运行时请求了没有注册的名称。两处检查不能相互替代，也不需要调用模型来验证。

### 理解后再编写

本步只修改 `src/tools/tool-registry.service.ts` 的构造函数。在现有 `set` 之前，用 `Map.has` 判断名称是否已注册；重复时抛出清晰错误，例如 `重复工具名：search_user_assets`。

注册表只检查名称冲突，不判断 `query` 等业务参数。参数检查仍由具体工具负责；本步不修改 Gateway、不增加 HTTP 接口，也不实现循环。
