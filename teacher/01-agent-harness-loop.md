# 第一课：一次提问背后的 Agent Loop 与 Harness

本课先理解模型、Agent、Harness 的分工，再通过亲手编写的程序验证。项目已经清空原实现，下面的流程是教学示例，尚未实现。

本轮采用文档先行：先阅读、提问并复述，理解后再指导编写。阅读时抓住三个问题：谁决定下一步、谁执行工具、谁发起下一次模型请求。

## 模型、Agent、Harness

以下采用本次分享的工程视角，不同框架的命名边界可能不同。

| 概念 | 在短剧工坊里的职责 |
|------|--------------------|
| 模型（LLM） | 根据当前输入生成内容，或提出下一步动作 |
| Harness | 组织上下文、调用模型、执行工具、保存状态并实施权限和预算控制 |
| Agent | 结合模型决策与执行环境，围绕目标推进任务的系统 |

Agent 描述整体目标导向系统，Harness 描述支撑其运行的软件部分，模型承担其中的理解、生成与动作选择。同一套运行时可以通过不同提示词、工具和模型配置承载不同任务。

### Agent 与 Harness 是不是同一个概念？

不是。在本课的工程视角下，可以用一个便于记忆的公式理解：

**Agent ≈ Model + Harness。**

这里是概念上的组合，不是严格的行业统一定义，也不是把任意模型接上一个外壳就一定构成 Agent。我们关注的是：系统能否围绕目标，让模型根据当前信息选择行动，并通过执行结果继续推进任务。

- **Model（模型）**：理解需求、生成剧本、提出计划、选择要调用的工具及参数。模型响应里的工具调用，是一个待执行的请求。
- **Harness（运行支撑层）**：包围模型的工程系统。它准备提示词和上下文、发起模型请求、校验并执行工具调用、保存消息和任务状态，以及落实审批、预算、取消和停止规则。
- **Agent（智能体整体）**：模型与这些运行机制结合后，围绕用户目标工作的完整系统。本项目中的“短剧工坊 Agent”就是我们要逐步搭建的整体。

可以把模型比作会判断方向的驾驶员，Harness 比作车辆的控制与执行系统，Agent 则是两者结合后能够完成行程的整体。比喻只帮助理解分工，具体行为仍要看程序如何实现。

### 放到短剧工坊中，分别是谁在做事？

假设用户说：“根据这个剧本生成三个视频镜头，预算不要超过我设定的金额。”

| 环节 | 模型负责什么 | Harness 负责什么 |
|------|--------------|-----------------|
| 理解任务 | 理解剧情，提出分镜和行动建议 | 将用户需求、当前剧本、工具说明和约束组装成上下文，并请求模型 |
| 请求工具 | 提出视频生成工具调用及参数 | 校验参数，检查权限、预算与审批状态，满足条件后调用工具 |
| 获取进度 | 根据收到的状态信息决定如何回复或继续行动 | 保存视频任务 ID，按程序规则查询任务状态，记录工具结果 |
| 继续或结束 | 根据结果提出下一步动作，或生成最终答复 | 追加工具结果，必要时再次请求模型；遇到取消、预算限制或步数上限时停止 |

**模型提出动作，不代表动作已经执行；模型建议继续，也不能绕过 Harness 的控制规则。** 视频接口的实际提交和查询由工具及供应商适配代码完成，它们属于我们搭建的执行环境。

还要区分两种“规划”：模型可以提出“先拆分镜，再生成视频”的任务计划；Harness 则负责维护计划状态、安排执行和控制边界。对于已经确定的步骤，程序也可以直接编排，无须每一步都让模型重新决定。

### 为什么要单独学习 Harness？

同一个模型，配上不同的上下文、工具、状态管理和执行规则，可能表现出很不同的任务完成能力。因此，学习 Agent 不能只看模型输出，还要看一次任务是怎样被程序持续推进的。

后续我们亲手写的消息保存、Agent Loop、上下文压缩、工具执行、审批和预算控制，都是在逐步搭建 Harness。前端负责展示和交互；仅有聊天界面，还不足以说明背后的 Agent 运行机制。

参考：[Harness 工程实践](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)。

## 一次提问可以包含多次模型调用

假设用户提出“找雨夜机场素材，并写成三镜分镜”，可以这样处理：

| 步骤 | 发生了什么 | 调用类型 |
|------|------------|----------|
| 1 | 模型提出素材搜索请求 | 第 1 次模型调用 |
| 2 | Harness 执行搜索，得到实际结果 | 工具执行，本例不调用模型 |
| 3 | Harness 将结果交回模型，模型生成分镜 | 第 2 次模型调用 |

这个例子是一次用户提问、两次模型调用、一次工具执行。模型第一次提出搜索时，还没有拿到实际结果；Harness 发起下一次请求，模型才有机会依据新信息继续处理。

对于我们定义的工具，模型提出调用请求，执行系统找到对应函数并执行，之后将结果交回模型。参考：[工具调用往返说明](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)。

## Agent Loop

反复组织“调用模型 → 执行工具 → 回传结果”，就构成本课要实现的工具反馈循环。模型可以根据结果提出新的动作；Harness 负责继续调用，并按规则处理结束、预算、取消或错误。

模型一次响应结束后，下一次请求由 Harness 发起。消息历史和工具结果由程序管理，不代表模型参数在这次任务中被更新。

固定 Workflow 则由代码预先规定步骤路径；模型动态选择行动与固定编排都可以服务于业务目标。参考：[Workflow 与 Agent 的架构区分](https://www.anthropic.com/research/building-effective-agents)。

## 从普通程序走向第一次模型调用

| 阶段 | 程序做什么 | 模型调用次数 |
|------|------------|--------------|
| 接住需求 | 保存“写一个三镜短剧”并打印到终端 | 0 次 |
| 请求模型 | 把需求发送给模型服务，得到一次响应 | 1 次 |
| 推进 Agent 任务 | 根据模型响应执行工具，再把结果交回模型继续处理 | 可能多次 |

打印需求只能证明普通程序已经运行。要让模型处理需求，还要发出真实模型请求；要演示本课的工具反馈循环，还要执行工具并将结果交回下一次模型调用。
