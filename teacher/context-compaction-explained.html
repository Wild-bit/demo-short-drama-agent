上下文压缩：prepareTurnInput
十岁版说明书

这个函数决定：每次问模型之前，要从长长的聊天记录里挑哪些内容带过去，挑不下的旧内容怎么变成一张便利贴。

🎒 先记住一个画面：模型每次只能看一个限量书包。 聊天记录是越来越多的卡片，你要在每次提问之前，把卡片整理成一包能塞进书包的； 塞不下的旧卡片，写成一张便利贴，让模型「看一眼就知道旧事」。

03逐行读 prepareTurnInput

private async prepareTurnInput(history, turn, tools, budget, trace) {
  // ① 拿走已经写进便利贴的旧卡片
  const liveHistory = history.filter(
    ({ sequence }) => sequence > (turn.activeCheckpoint?.coveredThroughSequence ?? 0),
  );

  // ② 准备一台「打包机快捷按钮」
  const assembleInput = (entries, checkpoint) => buildModelInput(...);

  // ③ 第一次打包
  const input = assembleInput(liveHistory, turn.activeCheckpoint);

  // ④⑤ 两个条件都满足，才去写便利贴
  if (turn.summaryModelCallCount > 0 || input.inputSizes.droppedHistoryMessages === 0) {
    return input;
  }

  // ⑥ 写便利贴后再打包
  return this.summarizeContext(liveHistory, input, assembleInput, turn, budget, trace);
}
① 拿走旧卡片

sequence > coveredThroughSequence ?? 0

便利贴没写过时，?? 0 等于「从第 1 号卡片开始全带」。 写过，就从便利贴覆盖的下一号开始拿。 这样模型不会既看便利贴又看原文，免得同一件事听两遍。

② 打包机快捷按钮

assembleInput 只留两个旋钮

把不常变的四样东西提前填好：系统提示词、本轮消息、工具清单、书包容量； 只留两个旋钮——哪些历史、哪张便利贴。

每按一次都重新打包，不缓存结果。所以后面能用不同便利贴各打包一次来比较。

③ 第一次打包

拿到 input

里面装着打包好的消息（request）和打包记录（inputSizes）。

④⑤ 提前返回条件

if (A || B) return input;

A = summaryModelCallCount > 0：这轮已经写过便利贴。 一次问答最多写一次，不重复写——写便利贴要额外问一次模型，又慢又花钱。
B = droppedHistoryMessages === 0：一张卡片都没被挤出去，书包还装得下，没理由写。

这是或：A、B 里只要有一个成立，就直接返回第一次的打包结果。 反过来，能走到写便利贴那一步，需要两个都不成立。

A：已写过？
summaryModelCallCount > 0		B：没丢卡片？
dropped === 0		结果
否否写便利贴（唯一会写的一行）
否是直接返回
是否直接返回
是是直接返回

写成正面的「去写」条件就是 !A && !B，也就是 summaryModelCallCount === 0 && droppedHistoryMessages > 0。 代码保留 A || B 的「提前返回」写法，是为了让主路径少一层缩进。

⑥ 进入摘要

两个条件都满足 → summarizeContext

任何一个不满足，直接返回第一次的打包结果。

分支 A

没有可写的材料 → 直接返回原输入

prepareHistorySummary（compaction.ts:46）只挑完整、连续的旧轮次： 一轮必须从用户提问开始，以「没有工具调用的助手回答」结束； 每条只取前 400 个字符；装进摘要请求就继续加，装不下就停。

挑不到 → 不写便利贴，本轮照常进行。
分支 B

便利贴不合格 → 不采用

summarizeHistory（compaction.ts:109）有三道体检：

  1. 正文不能是空的
  2. 不能超过 900 字节（便利贴每轮都要用，太长反而占地方）
  3. 必须比它替换掉的旧卡片更省空间

任何一条不过 → checkpoint 是 undefined。

分支 C

便利贴自己装不进书包 → 不采用

拿到合格的便利贴，重新打包一次。如果打包记录说 summaryIncluded = false（便利贴加上必须留的内容超过书包容量），也不采用。

防止「为了省地方反而塞爆书包」。
分支 D

三关全过 → 采用

turn.activeCheckpoint = checkpoint 换成新便利贴， nextInput 换成新打包结果。 函数返回后，主循环拿这份新输入去问模型。

分支 E

写便利贴时出事了 → 用原输入继续

摘要模型超时、503 都走这里：

① 先问一句「是不是用户按了停止键？」是 → throwIfAborted() 真正中止。
② 不是 → 记一条 warn 日志，返回原来的打包结果。

便利贴写坏了不影响本次回答，只是模型看不到那么早的旧事。
附注

trace.recordModelCall("summary", ...)

写便利贴是一次真实的模型调用，会计入运行轨迹， 前端能看到「这轮为什么多花了一次调用」。

05prepareHistorySummary：挑哪些旧卡片写进便利贴

分支 A 里提到的这个函数（compaction.ts:46）不请求模型，只负责挑选： 从被挤出书包的旧卡片里，挑出一批可以安全写进便利贴的完整轮次，拼成一份要交给模型的摘要请求。

方向名字是什么
拿进来omitted被挤出书包的旧卡片，即 liveHistory.slice(0, dropped)
拿进来previous旧便利贴，可能没有
拿进来inputBudgetTokens摘要请求自己也不能超过的书包容量
交出去request要发给 DeepSeek 的摘要请求
交出去coveredThroughSequence新便利贴会贴到第几号卡片
交出去displacedInput新便利贴要替换掉的内容有多大，用来验收便利贴
交出去undefined一轮都没挑中，这次不写便利贴

例子：旧便利贴贴到第 4 号，被挤出去的是第 5–10 号

序号谁说的内容属于哪一轮

6助手发起 search_user_assets 调用轮 A
7工具搜索结果（很长）轮 A
8助手「找到三张：思考、探头、招手」轮 A

10助手「夜晚的窗台」轮 B
 
export function prepareHistorySummary(omitted, previous, inputBudgetTokens) {
  // ① 从旧便利贴的位置起步
  let coveredThroughSequence = previous?.coveredThroughSequence ?? 0;
  let displacedInput = previous ? 旧便利贴的大小 : 0;

  // ② 按用户提问切成整轮，一轮一轮看
  for (const turn of splitHistoryTurns(omitted)) {
    const last = turn.at(-1);

    // ③ 四项检查，有一项不过就停
    if (
      turn[0].sequence !== coveredThroughSequence + 1 ||
      !last ||
      last.sequence !== coveredThroughSequence + turn.length ||
      last.message.role !== "assistant" ||
      last.message.toolCalls?.length
    ) break;

    // ④ 只留用户看得见的卡片，每张最多取 400 个字符
    const visible = turn.filter(isVisibleMessage);

    // ⑤ 试装：加上这一轮后，摘要请求超预算就停
    if (estimateDeepSeekInputTokens(candidate) > inputBudgetTokens) break;

    // ⑥ 装得下，正式记账
    coveredThroughSequence = last.sequence;
    displacedInput += 这一轮可见卡片的大小;
  }

  // ⑦ 一轮都没挑中，就不写便利贴
  if (coveredThroughSequence === (previous?.coveredThroughSequence ?? 0)) return undefined;
  return { request, coveredThroughSequence, displacedInput };
}

上面是节选，省略了拼装 transcript 和 candidate 的细节，判断和顺序与源码一致。

① 起点

从旧便利贴停下的地方接着写

例子里 coveredThroughSequence = 4。没有旧便利贴时从 0 起步。 displacedInput 先记上旧便利贴的大小，因为新便利贴会把旧便利贴一起换掉。

② 切成整轮

splitHistoryTurns：每遇到一张用户卡片，就开新的一轮

例子切成两轮：轮 A 是第 5–8 号，轮 B 是第 9–10 号。

③ 分支 · 四项检查

有一项不过 → break，这一轮和后面的都不挑

检查轮 A 的实际值防的是什么
turn[0].sequence === covered + 1 5 = 4 + 1 ✓ 和上一张便利贴之间不能有空洞
last.sequence === covered + turn.length 8 = 4 + 4 ✓ 这一轮里面不能缺卡片
last.message.role === "assistant" 第 8 号是助手 ✓ 这一轮必须有结尾
最后一张没有 toolCalls 第 8 号是最终回答 ✓ 停在工具调用的半轮不写进便利贴

代码里的 !last 只是给 TypeScript 看的空值保护。

用「停」而不是「跳过」：便利贴只用一个数字表示「到这里为止都概括了」，跳过中间一轮去写后面的，这个数字就不准了。
④ 只留看得见的卡片

isVisibleMessage：用户提问 + 助手最终回答

轮 A 只留第 5 号和第 8 号。第 6 号工具调用、第 7 号工具结果不交给写便利贴的模型。 每张超过 400 个字符的只取开头，后面加 …。

⑤ 分支 · 试装

摘要请求超预算 → break

把「已经挑好的 + 这一轮」拼成候选请求：一条系统指令（summaryInstruction）， 加一条装着旧便利贴和挑中原话的用户消息。 候选请求比书包容量大，这一轮就留到以后再写。

⑥ 装得下 → 记账

覆盖点往前推一轮

轮 A 记账后 coveredThroughSequence = 8，displacedInput 加上第 5、8 号的大小。 轮 B 再走一遍 ③–⑥：9 = 8 + 1 ✓，10 = 8 + 2 ✓，装得下，覆盖点推到 10。

⑦ 分支 · 收尾

覆盖点没动 → 返回 undefined

会落到这里的四种情况：

  1. omitted 是空的，没有被挤出去的卡片
  2. 第一轮的序号接不上旧便利贴
  3. 第一轮停在工具调用或工具结果，没有最终回答
  4. 第一轮的摘要请求就超预算
这时不会请求模型，summaryModelCallCount 也不加 1，因为计数写在 if (!batch) return input 之后。
容易漏看

覆盖点是程序算的，不是模型说的

模型只负责写便利贴上的字。贴到第几号，取的是每轮最后一张卡片的序号。 所以第 6、7 号虽然没交给模型，覆盖点照样越过它们，下次这四张都不再以原文发送。

容易漏看

displacedInput 只算看得见的卡片

它是 summarizeHistory（compaction.ts:119）验收便利贴的门槛：新便利贴必须比它小才采用。 工具调用和工具结果没算进去，门槛偏小，要求更严： 新便利贴至少要比「旧便利贴 + 这些问答原话」更省地方。

06打包机里的三道关口

关口一 本轮消息 fitCurrentTurn · context.ts:188

本轮是「主角」，必须装进去，也不能靠便利贴救。装不下只能撕工具结果。

称重：system + 本轮 + 工具说明书 ≤ 书包？
是 → 过关
否 → 撕第一档：素材结果去掉描述和标签，保留 ID/名称/类型/链接 → 重称
还是否 → 撕第二档：链接也去掉 → 重称
还是否 → 💥 413：本轮输入超出预算，请缩短消息
关口二 便利贴 buildModelInput
没有便利贴 → 不带
有，但加上后超容量 → 不带（便利贴仍存在会话里，以后再用）
有，并且装得下 → 带（summaryIncluded = true）
关口三 历史 fitRecentHistory · context.ts:216
把历史按「用户提问」切成整轮（groupCompleteTurns）
从最新一轮往前：
这一整轮放得下 → 装进去，继续看前一轮
放不下 → 立刻停，不跳过它去装更老的
开头不成整轮的消息（比如历史从一条工具结果开始）→ 永远不装

为什么不跳过？因为历史里如果有「没有问题的回答」或「没有回答的问题」，模型会误读。 要么整轮带走，要么整轮留下。

结果就是两个数：保留了哪些卡片、droppedHistoryMessages 是多少。 后者正是下一次写便利贴的原料。
