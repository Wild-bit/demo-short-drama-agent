# 第一课讨论记录：从工具请求到执行闭环

日期：2026-11-02。

配套讲义：[一次提问背后的 Agent Loop 与 Harness](./01-agent-harness-loop.md)。本记录整理本次提问、回答和校准结果，作为后续动手与技术分享的复习材料。当前只完成概念讨论，尚未编写或验证实现代码。

## 1. Model、Harness、Agent 分别是什么？

本课采用工程视角：**Agent ≈ Model + Harness**。这是帮助理解的表达，不是严格的行业统一定义。

| 概念 | 分工 |
|------|------|
| Model | 理解需求、生成内容、提出计划、选择工具与参数 |
| Harness | 组装上下文、请求模型、校验与执行工具、保存状态，以及控制权限、审批、预算和停止条件 |
| Agent | 模型与运行机制结合后，围绕目标推进任务的整体 |

模型可以提出任务计划，Harness 保存和推进执行状态。确定的业务步骤也可以直接由程序编排，不必每一步都请求模型决定。

## 2. 模型说要生成视频，视频开始生成了吗？

**没有。模型提出工具调用，只表示它请求执行一个动作。**

本次最初的理解是：“Harness 重新组织上下文和工具列表，再调用模型。”其中重新组装上下文和再次调用模型是后续环节，前面还需要检查并真正执行工具。

一次典型过程是：

1. 模型返回正式工具调用，包括调用编号、工具名称和参数。
2. Harness 检查工具、参数、权限、预算和必要审批。
3. 检查通过后，执行工具，调用视频服务。
4. 保存真实执行结果。异步视频服务可能只返回任务 ID，此时代表已提交，不代表视频已生成。
5. 按流程规则决定：继续查询、将结果交回模型，或结束任务。

下一次模型请求由 Harness 发起。工具列表可以按阶段或权限调整，但不必每轮重新生成。

## 3. 工具返回“余额不足”，该交给模型什么？

本次回答：“把余额不足的错误码和错误信息交给模型。”这个理解正确。

还应保留它与原工具调用的对应关系，例如：

| 信息 | 教学示例 |
|------|----------|
| 原工具调用 | `call_001`：生成第一个镜头 |
| 对应工具结果 | `call_001`：提交失败 |
| 错误码 | `INSUFFICIENT_BALANCE` |
| 错误信息 | 余额不足，未创建视频任务 |

这些字段仅用于说明概念，实际协议在接入 API 时确定。回传的是经过必要整理的真实结果，不应包含 API Key 等敏感信息。

模型可以据此解释问题、提出下一步建议；重试或切换供应商仍须经过 Harness 的规则检查。

## 4. 工具失败后，一定要再次调用模型吗？

**不一定。用户认为两种做法都可以，这个判断正确。**

| 业务需要 | 可采用的处理 |
|----------|--------------|
| 规定余额不足就结束 | Harness 直接展示错误并结束 |
| 需要结合整项任务解释进度、整理建议 | 将结果交给模型，再生成答复 |
| 后续动作依赖对工具结果的理解 | 将结果交给模型，继续推进 |

例如前三镜中，前两镜已提交、第三镜余额不足：程序可以直接展示各镜状态，也可以让模型结合状态组织说明。后者增加模型调用的时间与费用，应有实际用途。

因此，**一次提问可能包含多次模型调用，但不要求工具执行后必须再次调用模型。** Harness 掌握程序执行控制权，模型在允许范围内提出行动建议。

## 5. 如何区分普通回答和工具调用？

本次理解：“工具调用通常是结构化数据，普通回答比较自由。”方向正确，需要区分以下概念：

| 概念 | 含义 |
|------|------|
| JSON Schema | 工具参数的格式说明，例如字段类型和必填要求 |
| 工具调用参数 | 模型实际给出的参数数据，需要按 Schema 和业务规则校验 |
| 模型响应类型或结束原因 | 帮助程序识别回答或工具调用，具体以 API 协议为准 |
| 工具执行状态 | 实际操作成功、失败、已提交或运行中等状态 |

普通回答的外层也有 API 响应结构，内容可以是自由文本，也可以按要求输出 JSON。**不能仅凭“是不是 JSON”判断工具调用，应识别 API 约定的工具调用字段。**

模型提出调用时，尚不知道真实执行结果；结构化参数也不等于参数正确。

## 6. 只输出“我现在调用视频工具”，常规怎么处理？

**先按普通文本处理，不执行工具。** 是否继续请求模型，取决于任务状态和预先设计的流程规则。

如果用户要求生成视频，但系统没有正式工具调用，也没有已提交的视频任务，可以进行有限次数的纠正：

> 当前尚未提交视频生成任务。如果需要生成视频，请使用 `generate_video` 工具；如果无法继续，请说明原因。

下一次响应若包含正式调用，再做工具与参数检查；仍不满足要求且达到重试上限，就停止并说明未能提交任务。不能把普通文本伪造成一次真实工具调用或工具执行失败。

任务是否完成，应依据真实状态，例如任务 ID 和供应商返回状态，不能只相信模型说“已经开始生成”。普通回答如果已经满足用户需求，则不需要纠正。

若流程已经确定必须调用工具，可以在 API 支持时使用工具选择配置约束模型；若工具及参数都已确定，也可以直接由程序执行。

## 7. 两种失败的区别，以及本次教学校准

本次回答的核心是：“不执行，把问题反馈给模型，让它修正输出。”**这个核心思路正确。** 讲解时不应把细分区别说成整体判断错误。

需要校准的是失败位置：

| 情况 | 失败位置 | 如何继续 |
|------|----------|----------|
| 只有普通文本，但流程要求发起工具调用 | 预期动作没有发生，尚未进入工具校验 | 补充任务未完成的信息，按规则纠正 |
| 有正式工具调用，但工具不存在或参数有误 | 工具调用校验失败 | 拒绝执行，按协议反馈校验问题 |
| 合法调用已执行，但供应商返回余额不足 | 实际工具执行失败 | 保存真实错误，直接结束或交回模型 |

这些情况都可能通过追加相应信息、重新组装上下文、再次请求模型来处理，但不能混淆发生的事实。通常保留原有指令和必要消息，追加新信息，不必每次重写提示词。纠正和重试必须有次数或预算上限。
