# 第二课：从打印需求到第一次模型调用

日期：2026-11-03。状态：讲义已准备，真实 API 调用尚未实现或验证。

## 本课目标

第一课的程序保存需求并打印，模型调用次数为 0。第二课让程序把需求发送给 DeepSeek，等待响应，再打印模型生成的文本。

本课只做一次非流式文本请求，不加入工具、循环、视频或前端。完成一次模型调用，还不代表已经实现完整 Agent。

## 1. 一次请求经过什么过程？

用户需求 → 程序组装消息 → HTTP 请求 → DeepSeek 服务生成响应 → 程序检查并读取结果 → 终端展示。

本课拟先使用 Node.js 的 `fetch`，直接观察请求和响应；暂不引入框架或 SDK。之后按需要抽成 Gateway，避免把业务代码与厂商协议混在一起。

## 2. 请求需要哪些信息？

| 信息 | 用途 |
|------|------|
| 接口地址 | 请求发往哪里 |
| API Key | 服务端鉴权，不属于发给模型的业务消息 |
| model | 指定模型 ID |
| messages | 本次交给模型的消息列表 |
| stream | 本课设为 false，先拿完整响应；SSE 后续学习 |

官方当前提供 `POST https://api.deepseek.com/chat/completions`。本课核查时官方首次调用示例使用 `deepseek-flash`；实际接入前确认账户权限。第三方或公司网关的地址、模型名称和权限可能不同，不能直接套用官方配置。[DeepSeek 首次调用说明](https://api-docs.deepseek.com/zh-cn/)

### messages 为什么不是只有一句字符串？

消息需要表达“谁说了什么”。本课先用两种角色：

- `system`：程序设定的任务说明，例如“你是短剧编剧，请简洁回答”。
- `user`：用户实际提出的需求，也就是当前 `userRequest`。

模型生成的回答属于 `assistant`。后续工具结果属于 `tool`，到工具课程再接入。

例如本课会准备这样的业务内容：

| role | content |
|------|---------|
| system | 你是短剧编剧，请用中文简洁回答。 |
| user | 写一个雨夜重逢的短剧，拆成三个镜头。 |

API Key 放在请求头中用于鉴权，不放进这张消息表，也不写进提示词。

## 3. 收到的响应不是单独一段剧本

API 返回的是响应对象。我们需要区分 HTTP 状态和响应正文中的业务字段。

| 信息 | 观察什么 |
|------|----------|
| HTTP 状态 | 请求是否成功，失败时检查实际错误 |
| id | 本次响应标识，便于排查 |
| choices[0].message.content | 本课关心的最终回答文本 |
| choices[0].finish_reason | 本次输出怎样结束，例如正常停止或达到长度限制 |
| usage | 服务返回的 token 用量，不等同于直接给出人民币费用 |

本课不把任意 HTTP 响应都当成功，也不把 `content` 为空直接当成成功生成。实现时检查必要字段；TypeScript 类型声明不能替代对真实响应的运行时检查。[DeepSeek Chat Completions 协议](https://api-docs.deepseek.com/api/create-chat-completion/)

Token 是模型处理内容的计量单位，不等于字符或汉字数。实际费用还与模型和计费规则有关，本课先记录用量，不写死价格。

## 4. 为什么下一次请求还需要带上消息？

在本课采用的 Chat Completions 消息方式下，不能只凭同一个 API Key 就假设服务记住了上一轮需求。程序需要把下一次所需的消息放进请求。

例如下一句“把第二个镜头改成白天”，如果没有相关剧本和历史，模型就缺少修改对象。后续由 Harness 保存历史，再决定每次选哪些消息；上下文管理与压缩课程会深入解释。

API Key 用于鉴权，不是会话内容。消息历史也不代表模型参数被更新。

## 5. 凭证与失败如何处理？

- 真实凭证由用户保存在本地 `.env`，不发到聊天中，不写进源码或日志。
- `.env.example` 只写变量名与占位值，用于说明配置；现有 `.gitignore` 已排除真实 `.env`。
- 创建 `.env` 不会自动让程序读取它；动手时明确配置加载方式。
- 缺少 Key 时，在本地报出清晰错误，不发送空凭证请求。
- API 拒绝请求时，区分鉴权、余额、参数、限流等真实原因；输出必要状态和脱敏错误，不打印请求头。
- 本课不做自动重试。网络超时未必表示服务端未处理，应明确报告结果未获取，避免无意识重复调用。

## 6. 理解后再亲手编写

按小步推进，不一次性搭好所有文件：

1. 用户配置环境变量与加载方式，只验证是否存在，不打印 Key。
2. 定义最小文本请求和结果类型，逐步创建 `src/gateway/text/types.ts`。
3. 创建 `src/gateway/text/deepseek.ts`，完成一次 HTTP 请求、必要检查和结果提取。
4. 在 `src/main.ts` 调用这个入口，打印模型回答与本次用量。
5. 执行类型检查，再由用户运行一次真实请求，确认输入、输出与失败提示。

真实请求通常会产生 API 费用。先用简短需求验证，暂不进行批量调用。

验收：缺少配置时清晰报错；有效配置下一次请求得到非空文本；能解释消息角色与结果字段；类型检查通过。未实际观察到的失败路径，不标为已验证。
