# 第三课：如何约束模型输出剧本与分镜

日期：2026-11-05。状态：已定义业务类型并编写顶层校验；当前转入提示词与结构化输出，尚未验证受约束的真实生成。

## 1. 从能读到能用

第二课获得了一段 Markdown 回答。前端若要分别展示、编辑剧名和镜头，就需要稳定字段，而不是从任意段落中猜测结构。

本课先约定一个简化产物：剧名、梗概，以及可编辑的分镜草案。每个镜头包含场景、画面动作、对白。这里是教学用简化分镜，不是完整影视生产规范。

目标路径：用户需求 → 装配消息 → Gateway 请求模型 → 提取回答 → 解析 JSON → 校验业务结构 → 得到可供页面使用的产物。

## 2. 数据约定

| 字段 | 用途与规则 |
|------|------------|
| title | 非空剧名 |
| synopsis | 非空剧情梗概 |
| shots | 非空镜头数组，数组顺序表示播放顺序；数量按本次需求校验 |
| shots[].id | 唯一的正整数序号，便于本课定位镜头 |
| shots[].scene | 非空场景描述，如时间、地点 |
| shots[].visual | 非空画面与动作描述 |
| shots[].dialogue | 字符串；没有对白时允许空字符串 |

暂不加入视频供应商、视频任务 ID 和审批状态，它们不是本课的创作内容字段。本课序号也不是未来跨版本编辑的永久标识，后续按需要演进。

## 创作流程与范围约定

用户可以提供创意、剧本或已有分镜；Agent 起草或辅助修改，用户可以编辑、增删镜头。草案确认后，再估算费用和确认生成范围，视频任务以用户确认版本为依据。

初期演示可以使用三个镜头，但不将数量写死。第一版采用对话区与分镜列表，支持字段编辑和增删；无限画布、复杂时间线、版本对比与多人协作作为扩展。需要对话修改时先展示完整新草案，不提前引入复杂局部更新协议。

第三课只实现可校验的草案，后续课程再实现页面编辑、服务端确认状态与生成审批。已确认内容变更后，不能沿用旧审批提交新增或改变的付费任务。

## 3. 三种约束分别解决什么？

| 约束 | 作用 | 局限 |
|------|------|------|
| 提示词 | 说明创作任务、字段含义、镜头数量、输出要求 | 模型可能没有完全遵循 |
| 接口的结构化输出能力 | 在支持范围内约束生成格式 | 具体支持程度接入时查官方文档；合法 JSON 不等于符合业务 |
| 程序校验 | 检查收到的数据，拒绝不合格结构 | 字段正确不等于剧情好看或画面可拍 |

`JSON.parse` 只检查文本能否解析为 JSON。例如 `{"shots": []}` 是合法 JSON，却不符合非空分镜草案的要求。

TypeScript 类型只在开发检查中生效。将解析结果断言成剧本类型，不会自动检查字段或镜头数量。接收结果仍需最小运行时检查，但不继续堆叠逐字段手写判断。复杂规则后续可用 Schema 集中描述；校验是验收手段，不是本课主线。

## 4. 提示词怎么装配？

- 稳定的创作角色、字段说明、业务约束放在程序维护的提示词中。
- 用户具体剧情放在 `user` 消息中。
- 将提示词提取到 `src/prompts/`，由业务层组织后传给 Gateway，不把短剧规则塞进通用 HTTP 客户端。

本课讲的提示词装配，是程序正常组织指令与输入。安全语境的 Prompt Injection 则是输入或外部资料试图越过其可信边界、改变系统行为，两者不要混用。

镜头数来自用户需求或模型建议，不作为固定系统规则。用户明确指定数量时，校验实际数量是否符合本次要求；未指定时，允许模型提出合理数量。把规则写进 system 不代表执行已经得到保证。安全边界与资料注入会在后续上下文课程深入讨论。

## 5. 哪里负责解析与校验？

| 层次 | 本课职责 |
|------|----------|
| request | 发送 HTTP 请求、解析接口外层 JSON |
| gateway/text | 提取厂商响应中的回答文本 |
| prompts | 定义创作说明，组织模型消息 |
| domain | 定义剧本类型，解析并检查业务数据 |
| main | 串联流程，展示产物或错误 |

接口响应是外层 JSON；回答文本内部若采用 JSON 格式，还需再解析为业务对象。这是两个不同层次。

不要在通用请求工具里加入分镜数量的检查，否则其他业务也会受到短剧规则限制。

## 6. 出错时先清楚失败，不自动修复

区分网络或接口失败、回答不是合法 JSON、字段与镜头数错误。保留能定位问题的提示，先由用户观察和处理，不在本课提前加入无限重试。

后续工具与 Loop 课程会把校验结果作为反馈，让模型有限次数地修正。只有需要新的模型理解或生成时，才增加一次模型调用。

结构通过后仍要人工检查剧情连贯、镜头是否包含过多动作、对白是否适合片长。这些不能由字段校验代替。

## 7. 调整后的学习顺序与验收

1. 明确输出协议：字段含义、单镜头粒度、镜头数量来源。
2. 创建 `src/prompts/storyboard.ts`，逐条理解角色、任务、业务规则、格式和示例，不先堆校验代码。
3. 同一需求先只改变提示词，观察相对原始回答的变化，不把单次成功视为稳定性证明。
4. 在当前 Chat Completions 请求中按需启用 `response_format: { type: "json_object" }`，提示词明确要求 JSON，并给出结构示例。格式配置按请求选择，不把所有文本调用强制设为 JSON。
5. 比较提示词约束与接口格式约束的作用；解析结果后做最小验收，字段结构不合格时清楚报错。
6. 记录格式、字段、镜头数量与镜头粒度的表现；不在本课扩展大段防御代码或自动重试。

当前官方 JSON Output 指南说明 Chat Completions 的 JSON 模式用法；JSON 模式不等于按业务 Schema 严格生成。官方 Responses API 另有 Schema 格式配置，不能把不同接口的参数直接混用。本课先沿用现有接口，不为此更换整条调用链路。

参考：[JSON Output 指南](https://api-docs.deepseek.com/guides/json_mode/)、[Chat Completions 协议](https://api-docs.deepseek.com/api/create-chat-completion/)、[Responses 协议](https://api-docs.deepseek.com/api/create-response/)。核查日期：2026-11-05。

每轮只指导其中一个小步骤，用户亲手编写。现有顶层校验暂保留，不要求补上之前的大段逐镜判断。
